# Hosted Multi-User Coolify MCP Bridge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and deploy a GitHub-authenticated hosted MCP bridge where every user stores and uses only their own encrypted Coolify connection.

**Architecture:** Add a tenant/authentication boundary around the existing Rust HTTP transport. GitHub OAuth establishes the human user, MCP PKCE grants are bound to that user, and a persistent encrypted SQLite store holds each user's Coolify URL/token and profile. The MCP application resolves a user-scoped `CoolifyClient` per request instead of using one global server credential. Keep local stdio and the Python fallback unchanged.

**Tech Stack:** Rust 2024, Axum 0.8, Tokio, reqwest/rustls, SQLite via `rusqlite` with bundled SQLite, `ring`/`aes-gcm` for AEAD, GitHub OAuth REST API, existing OAuth/PKCE, Caddy, Docker Compose, fake HTTP fixtures.

**Spec:** `docs/superpowers/specs/2026-09-20-hosted-multitenant-mcp-design.md`

## Global Constraints

- Hosted HTTP must not configure a global `COOLIFY_BASE_URL` or `COOLIFY_ACCESS_TOKEN`.
- Every authenticated request must resolve one tenant/user before loading a Coolify connection.
- HTTP defaults to `read-only`; writes, deletes, and deploys require the existing confirmation checks.
- Never log, serialize, return, audit, or image-layer GitHub secrets, Coolify tokens, OAuth codes, cookies, or raw tool arguments/responses.
- Persist `/data` with mode `0700`; database, key, OAuth state, and audit files must be mode `0600`.
- GitHub scopes are identity-only (`read:user` and `user:email` if needed); do not request repository or administration scopes.
- PKCE S256, exact redirect/resource binding, single-use state/codes, refresh-family replay revocation, bounded bodies, and rate limits remain mandatory.
- Preserve local Rust stdio, Python fallback, the 45-tool default roster, `mcp.social.dpdns.org`, and the existing Caddy route behavior until the new service is healthy.
- No real credentials may appear in source, tests, fixtures, docs, command output, or commits.

## Review Focus

- **OAuth transaction resumed after GitHub callback:** a valid MCP PKCE request must continue for the same client, redirect, resource, and authenticated user; test in Task 3.
- **Cross-tenant bearer reuse:** a token issued to user A must not resolve user B's connection or be accepted for a different resource; test in Task 4.
- **Token ciphertext and form leakage:** submitted Coolify tokens must not appear in SQLite plaintext, JSON, URLs, logs, errors, audit lines, or HTML; test in Task 2 and Task 5.
- **Connection lookup failure:** missing, deleted, rotated, or undecryptable connections must fail closed without falling back to a global client; test in Task 4.
- **Restart and key rotation behavior:** valid encrypted data survives restart with the same key, while a wrong key degrades health and refuses calls; test in Task 2 and Task 6.
